# Swati — Week 3: Defect-label validation (October 19–23, 2026)

## Objective
Improve the quality review of preliminary `candidate_defect` labels by inspecting commit-message evidence, detecting issue/PR references, flagging possible inconsistencies, and recording manual review findings.

## Existing label limitation
`ml/src/label_data.py` assigns candidate positive labels to files touched by commits whose messages contain defect-related keywords. This is a heuristic, not ground truth. A commit message can be misleading, an issue reference does not prove a defect fix, and a changed file may not contain the root cause.

## Implemented audit
Run:

```bash
python -m ml.src.audit_defect_labels
```

The audit reads:
- `data/raw/git_commit_files.csv` — commit/file records generated by `python -m ml.src.git_metrics`.
- `data/processed/preliminary_dataset.csv` — file-level features and candidate labels.

It writes:
- `reports/labels/label_audit.csv` — one row per dataset file, evidence counts, relevant commit hashes/messages, audit category, review status, and notes fields.
- `reports/labels/label_audit_summary.json` — category counts and limitations.

## Audit categories
- `positive_with_keyword_and_issue_reference`
- `positive_keyword_without_issue_reference`
- `positive_without_matching_keyword_evidence`
- `negative_with_keyword_and_issue_reference`
- `negative_with_issue_reference_only`
- `negative_with_keyword_evidence`
- `no_keyword_or_issue_reference_evidence`
- `invalid_candidate_label`

The categories prioritize records for review. They do **not** automatically identify a false label. Review the commit message, linked issue or pull request, and code diff before deciding whether a label is false, uncertain, or supported.

## Manual review procedure
1. Filter `label_audit.csv` to positive rows without issue references and negative rows with keyword/issue evidence.
2. Inspect the commit on the source repository and follow any issue/PR reference manually.
3. Confirm whether the issue describes a software defect and whether the commit fixes that defect.
4. Check the changed files and diff; a changed file is not necessarily the root-cause file.
5. Enter the conclusion in `review_status` and `review_notes`. Suggested statuses: `supported`, `likely_false_positive`, `likely_missed_positive`, `uncertain`, `not_reviewed`.
6. Keep the original `candidate_defect` value unchanged until the labeling methodology and evidence are reviewed and a documented relabeling decision is approved.

## Research limitations
- Issue references are detected from commit messages only; issue tracker content is not fetched automatically.
- The heuristic can miss defects with uninformative commit messages and can flag non-defect changes.
- No manual findings should be claimed until actual repositories and commits have been reviewed.
- Store source URLs/commit hashes in review notes when recording a human-reviewed finding.

## Completion evidence to record
- Number of dataset files audited.
- Number of rows in each audit category.
- Number of commits/issues manually inspected (actual count only).
- Examples of confirmed false positives, missed positives, and uncertain cases, with evidence.
- Remaining limitations and proposed next labeling improvement.
